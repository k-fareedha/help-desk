## Agreed data rules

- Products: unique name/code, active by default. Seed VF/Vanforces, TF/Taskforce, SO/Speak Order and their 17 listed modules idempotently without overwriting existing registry rows. Seed module codes as uppercase underscore slugs; unique within product.
- Customers: required name/code; optional email/phone; active by default. A customer may associate with multiple products. No customer sample data.
- Assignees: local demo directory, empty by default, manageable via API/UI; assignees are not authenticated users.
- New `/api/v1` tickets require product, category, priority, title, description. Module, customer, assignee are optional. Category values: Bug, Feature Request, Technical Support, Integration Issue, Performance Issue, General. Priority: Low, Medium, High, Critical. Status: Open, Triaged, In Progress, Testing, Resolved, Closed; any valid transition is allowed. Defaults: Open.
- Legacy tickets remain product/module/customer-unassigned. Backfill `General`, `Medium`, `TEX-{id:06d}`, and migration-time created/updated timestamps. Normalize known `open`/`closed` values to `Open`/`Closed`; preserve other unknown values. Preserve IDs, titles, descriptions, and status meaning.
- Dashboard `resolved_tickets` counts both Resolved and Closed tickets.
- Legacy `POST /tickets` continues to accept `{title, description}` and creates an explicitly unassigned `General`/`Medium` ticket. Existing route response shapes remain unchanged. New APIs use `/api/v1`.
- History records every changed editable business field. Comments are separate records. Use `Local demo operator` as the explicit demo attribution. Keep ticket mutation and history atomic. `resolved_at` is set on entering Resolved or Closed, retained across terminal states, and cleared when reopened to a nonterminal status.
- Future role proposal: Super Admin global; Product Admin, Support Engineer, Developer scoped to assigned products; Customer User restricted to their customer and associated products. This is documentation only.

## API contract

- Products: `GET/POST /api/v1/products`, `GET/PATCH /api/v1/products/{id}`; module list/create under `/products/{id}/modules`, patch `/modules/{id}`.
- Customers: `GET/POST /api/v1/customers`, `GET/PATCH /api/v1/customers/{id}`; PATCH accepts profile and `product_ids` together atomically. Membership-only replacement remains available with `PUT /customers/{id}/products` body `{ "product_ids": [1, 2] }`.
- Assignees: list/create/patch under `/api/v1/assignees`; deactivate rather than delete.
- Tickets: list/create/detail/patch under `/api/v1/tickets`; list query accepts `page` (default 1), `page_size` (default 25, max 100), `q`, `product_id`, `status`, `priority`. Response list envelope is `{items, page, page_size, total}`. Search ticket number/title/description. Sort newest first.
- Ticket create body: `{product_id, module_id?, customer_id?, title, description, category, priority, assigned_to?}`. Patch accepts editable fields. Comments: `POST /tickets/{id}/comments` body `{comment}`; history: `GET /tickets/{id}/history`.
- Dashboard: `GET /api/v1/dashboard/summary`, optionally filtered by product, returns totals (total/open/in-progress/resolved/critical), product counts, and recent tickets.
- Keep `/assistant` unchanged and isolated from ticket data. Do not remove `/tickets` aliases.
